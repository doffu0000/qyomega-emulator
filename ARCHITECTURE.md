# Architecture

This explains how the emulator is put together, what is known and what is assumed, and the
mistakes that cost the most time. The chronological logs are `EMU_STATUS.md` (the CPU and the
hardware) and `FRONTEND_STATUS.md` (the web page). Reverse engineering results are in
`../FINDINGS.md`.

## 1. Layers

```
 browser page (index.html, synth.js, sfengine.js)
        |  HTTP on 127.0.0.1 only
 server (serve.go, sysex.go, static.go)      runs the machine in a goroutine, paced to real time
        |
 Machine (machine.go, snapshot.go)           CPU + bus + devices + battery RAM, power cycling
        |
 CPU (cpu.go, decode*.go, operand.go, step*.go, interrupt.go)     H8S/2600, advanced mode
        |
 Bus (bus.go) with devices: on chip (onchip.go, tpu.go, sci.go), LCD (lcd.go),
        keys and lights (keys.go), sound CPU port (subport.go)
```

Everything that touches the machine happens under one mutex in the server. Nothing in the
program opens a MIDI port, and the server refuses to listen on anything but a loopback address.

## 2. The CPU

* The chip is Yamaha's SWX00B. The core is a Renesas H8S/2600 in advanced mode (24 bit
  addresses). The firmware's task switch uses `ldmac`, which the plain 2000 core lacks, which is how this
  was found.
* `decode_table.go` is generated by `gen_table.py` from MAME's `h8s2600d.inc` (BSD-3-Clause). The
  decoder matches opcodes against that table, `operand.go` decodes both operands, `step.go` and
  `step2.go` execute. An instruction that is not implemented returns `ErrUnimpl` instead of being
  skipped. Decoded instructions from flash are cached.
* Speed is about 17 million instructions per second on a current PC. The server paces the CPU to
  about real time: `realTimeRate = 16934400 / statesPerInstr`, that is a 16.9344 MHz clock (twice
  the 8.4672 MHz crystal in the service manual) at 3 clocks per instruction. Both numbers are
  inferred. Nothing depends on cycle exactness, only on the ratio between instruction count and
  timer ticks.
* Interrupts follow `SYSCR.INTM`. The firmware never writes SYSCR, so it runs in **mode 0**: the I
  bit masks interrupts, a stacked frame is CCR plus a 24 bit PC (no EXR word), and all interrupts
  are treated as one level. Mode 2 exists in the code for completeness.
* Vectors are read from the firmware's copy of the table at flash 0x10000 (the real table lives in
  the protected boot block and forwards there).

## 3. Memory map as the emulator sees it

| Address | What | Notes |
| --- | --- | --- |
| 0x000000 to 0x1FFFFF | Main flash, 2 MiB | Loaded from your image. 0x0 to 0xFFFF is the boot block, not in any update, so 0xFF. Starts at the reset handler 0x0DCEEA. |
| 0x200000 to 0x2FFFFF | Style ROM, 1 MiB | Not in the image, reads blank. Preset style headers (flash 0x1E0000 and up) are patched in memory with the firmware's own empty pattern header so pattern mode does not show nonsense. The file is not touched. |
| 0x400000 to 0x41FFFF | System and user SRAM, 128 KiB | Battery backed on the real unit: settings, songs, patterns. This is the memory a snapshot keeps across a reset. Magic `QY1X` (0x51593158 at 0x4044B8) means it has been initialised; without it the firmware wipes it and shows "Factory Set". |
| 0x600000 to 0x61FFFF | Work buffer RAM | |
| 0x800000, 0x800001 | LCD controller data and command/status | T6963C style, 128 by 64 pixels. |
| 0xA00000 | Key matrix reads, indicator latch writes | See section 5. |
| 0xC00000, 0xD00000 | SmartMedia control and data | Open bus, no card. |
| 0xE00000 | Byte port to the sound CPU | See section 6. |
| 0xFF0000 to 0xFFFFFF | On chip RAM and registers | Stack starts at 0xFFF45A. Register devices are layered on top. |

Reads of unmapped addresses return 0xFF and are logged. Accesses to on chip registers nothing
models read back what was written and are logged once per address. `emu run` prints both lists, and
an empty list is the sign that a code path does not rely on anything missing.

## 4. On chip devices (H8S/2655 register layout, confirmed by what the firmware does)

* **A/D converter** at 0xFFFF90: conversion completes at once, results default to 0x3C0 (an
  assumption).
* **TPU 0 to 2** at 0xFFFFD0, 0xFFFFE0, 0xFFFFF0 (`tpu.go`): counters, general registers, compare
  match with clear, overflow, flags, interrupts. The firmware's TPU0 setting (TCR 0x21, TGRA
  0x2112) gives exactly 2.000 ms at 16.9344 MHz, which is a strong sign the clock is right.
  Output pins and input capture do nothing. Channels 3 to 5 are not modelled.
* **SCI 0 to 2** at 0xFFFF78, 0xFFFF80, 0xFFFF88 (`sci.go`): asynchronous mode only. The MIDI
  ports are on these. `Machine.MIDIIn` feeds bytes to the receiver, transmitted bytes are logged
  and handed to a callback.

## 5. The LCD, the keys and the lights

* **LCD** (`lcd.go`): command and data protocol of the T6963C (parameters are written before the
  command). Text layer 22 by 8 cells of 6 by 8 pixels with the internal character ROM drawn from an
  approximate 5 by 7 font (cosmetic), character RAM for codes 0x80 and up, and a graphic layer.
  The mode byte selects OR, EXOR or AND of the two layers, which matters for the inverse selections
  the firmware draws.
* **Keys** (`keys.go`): the firmware drives one column at a time through the port byte at
  0xFFE029 (a one hot value from the table at flash 0x124AB8) and reads the row byte at 0xA00000,
  where **0 means pressed**. Names for keys come from a table in the firmware at flash 0x15A440
  (AMP, PARAM, SONG, PATTERN, SHIFT, EXIT, F1 to F4, MENU, CARD, cursor keys, NO and YES, ENTER, REC,
  TOP, STOP, PLAY, BWD, FWD, OCT DOWN, OCT UP, and the 25 micro keyboard keys written `k:E2` to
  `k:E4` with flats). A release sooner than 120 ms after the press is delayed, because a click
  would otherwise fall between two scans of the firmware.
* **Indicator latch**: a write to 0xA00000 sets the lights. It is **active low**: a light is lit
  while its bit is 0. Bit 0 is the beat light by PLAY (about 43 ms low on every beat while playing),
  bit 1 is the REC light (inferred, never seen to change), bit 2 is the AMP SIMULATOR light (lit at
  idle, the AMP key toggles it). `Keys.LED` holds the value and a bounded log (`LEDLog`, 512
  entries) keeps every change with a timestamp, which `/leds` serves.

## 6. Sound

The main CPU does not drive a tone generator directly. It sends the second SWX00B chip ordinary
MIDI and XG messages, one byte at a time, to 0xE00000: `F5 nn` selects the port (1 is parts 1 to
16, 2 is parts 17 to 32), then MIDI with running status and SysEx. `subport.go` collects these
bytes. The server serves them from an offset on `/tg` (with an epoch that changes on a power cycle,
so the page resets its synthesizer).

In the page, `synth.js` has a `StreamParser` that turns the bytes into channel events and XG
parameter changes, and a small built in synthesizer. `sfengine.js` (loaded on demand) plays the same
events on a soundfont through SpessaSynth. XG variation voices (bank LSB 1 and up) have no match in
a General MIDI soundfont, so `tools/buildvoicemap.py` makes a table that maps each unit voice to the
closest preset and adds small tonal changes. It is a judgement from the voice names, not from
listening to the unit.

Browsers only start audio after a click or key press, so the page keeps sound off at load and the
SOUND tab starts it.

## 7. The machine and snapshots

`Machine` (`machine.go`) owns the CPU, bus, devices and battery RAM. `NewMachine(path)` loads the
firmware image, sets the stack and starts at the reset handler. `PowerCycle(ram)` restarts it,
keeping the given battery RAM (or blank for a factory reset), which also replays the start up
pictures. `snapshot.go` writes the whole state, gzip compressed and guarded by a checksum of the
flash, with one routine used for both saving and loading so the two cannot drift apart.
`boot.snap` is a snapshot taken after the firmware has booted (about 130 million instructions) and
the popup was dismissed with EXIT.

## 8. The HTTP API (loopback only)

| Route | Purpose |
| --- | --- |
| GET `/firmware/state` | JSON `{state, message}`: `needfirmware`, `booting`, `ready` or `error`. Answered by the gate in `setup.go`, which wraps every other route |
| POST `/firmware` | Body is the user's firmware (Yamaha's update .mid or a 2 MiB image). Checked, saved as `sequencer_flash.bin`, then the unit boots. Refused with 409 once a unit is running and with 403 for cross site requests. Until the unit is up, `/` serves `setup.html` |
| GET `/midi/out?since=N` | Messages the unit sent on MIDI OUT after the safety filter (`midisafe.go`), each with its age in ms, plus counts of what was blocked |
| POST `/midi/in` | Live MIDI from the page into the unit's MIDI IN. At most 1 KB, same origin only, SysEx and system messages dropped |
| POST `/midi/policy` | Opt ins for the output: `{"Transport":bool,"ProgramChange":bool}`, both off by default |
| GET `/status` | JSON: program counter, instruction count, light latch, error text if the CPU stopped |
| GET `/leds?since=N` | Light latch changes with their age, so the page can replay them in time |
| GET `/screen.png` | The LCD as an image |
| GET `/keys`, POST `/key?name=X&down=1\|0` | Key names; press or release one |
| POST `/sysex` (raw `.syx` or hex text), GET `/sysex/progress` | Send SysEx to the emulated MIDI IN, replies in the body; progress of a long transfer |
| POST `/reset[?factory=1]` | Power cycle, keeping or blanking memory |
| GET `/tg?from=N&epoch=E` | Bytes sent toward the sound CPU, for the page's synthesizer |
| GET `/soundfonts.json`, `/soundfonts/NAME`, `/vendor/...` | Static files |

## 9. The page

`index.html` is one file (HTML, CSS and JavaScript) embedded in the program with `go:embed`, so
**every change to it needs a rebuild**. `synth.js`, `sfengine.js` and `setup.html` are embedded too;
`vendor/` and `soundfonts/` are read from disk.

* **Faceplate.** `#face` is laid out in faceplate units (1700 by 1000) by the `place()` helper:
  every part is positioned in percentages and sized in `cqw`, so the whole device scales as one
  picture. The `PANEL` table lists buttons as name, label, centre, size and style; `KEYS` lists the
  micro keyboard. The window is sized so the device fits the height of the screen.
* **Left strip.** `#soundtab` sits in a strip beside the faceplate and slides under the body edge.
* **Looks.** The root element carries `data-skin`. The base CSS is the Dark look; every other look
  is a block of rules scoped to `:root[data-skin="NAME"]` that overrides colours, gradients and
  shadows of the same list of parts (page, cards, faceplate, end caps, front lip, keyboard well,
  bezel, buttons, keys, lights, volume fader). Per look screen defaults live in the `DEFAULTS`
  and `BRIGHT` tables in the script. To add a look: copy a block, rename it, add an option to the
  dropdown and an entry in each table and in the list of valid names in the `<head>` script.
* **GM and XG** on the bezel are plain lettering (the `.xg` class), coloured by each look like the other lettering.
* **Screen swaps** the image only after the next frame has loaded, so it does not flicker.
* **SysEx** uses the exchange in `sysex.go`: each message is fed to the receiver and the server
  polls until the unit has taken it and had time to store it. The speed work (195 messages in about
  14 seconds after the speed work) came from not waiting for replies that never come and
  from batching, not from changing what the firmware sees.
* **`?ad`** hides everything under the device and fixes its size, used for screenshots and the
  promo video recording scripts in `scratch_ad/`.

## 10. Debugging workflow that worked

1. `emu run HEXPC COUNT` and read the unmodelled hardware list.
2. `emu watch` on an address range to see which code writes it, then `emu dis` there.
3. Compare with the Ghidra project of the firmware (see `../FINDINGS.md`).
4. Add the device or register with a test that fails first.

## 11. Verified, inferred, unknown

| Verified (the firmware behaves as expected) | Inferred (consistent, not proven) | Unknown or missing |
| --- | --- | --- |
| Boots to the SONG screen from reset | 16.9344 MHz at 3 clocks per instruction | Sound chip and wave ROM |
| Panel keys and the micro keyboard reach the firmware | A/D default values | SmartMedia card port |
| SysEx bulk dumps in and out, pattern data read back | REC light bit | Timer channels 3 to 5 |
| Timers raise the firmware's real handlers | One interrupt level for everything | The boot block (updater, recovery) |
| Light latch bits for beat and AMP | `trapa` semantics | Cycle exact timing |

A systematic comparison with recordings from a real unit has not been done. Giving the emulator
saved real dump files and requiring byte for byte equal replies is the cheapest next test.

## 12. Mistakes that cost the most time

* **`stm`/`ldm` register order.** Hand built task frames in the firmware depend on the exact order.
  Getting it wrong corrupted three registers on every task switch and the boot looked like a
  hang.
* **Interrupt mode.** Assuming mode 2 popped one word too many on `rte`. The firmware runs in mode 0.
* **PC bit 0.** The kernel pushes return addresses with bit 0 set as a marker. Hardware ignores it, so
  the emulator must clear it before fetching.
* **The core is H8S/2600, not 2000.** `ldmac` gave it away.
* **Key names off by one.** The name table is read one entry late by the firmware's own test, so
  every first guess named a key after its neighbour.
* **Active low everywhere.** Keys and lights both use 0 for "on". A debug row of dots drawn with
  1 for on looked random until this was clear.
* **Preset styles.** Pattern mode showed 553 BPM and garbage until the blank preset headers were
  filled in.
* **Waiting for replies.** The first SysEx path waited up to two seconds after every message, so a
  small file appeared not to load.
