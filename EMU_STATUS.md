- Step 6 done. Interrupt control mode 2 (priority in EXR.I2-I0): confirmed from the kernel stub at 0x104D4, which reads the frame as EXR at +0, CCR at +2, 24 bit PC after. `CPU.Raise(vec, level)` / `Lower(vec)` are the device API (level 1..7, level triggered: stays pending until the device lowers it, like a flag the firmware clears). Accepting an interrupt needs level > EXR.I2-I0, ties go to the lowest vector, the mask becomes the accepted level, T is cleared, sleep is woken. Vectors are read from flash 0x10000 + 4*vec (the firmware copy; the real table in the protected boot block forwards there). ldc/andc/orc/xorc block interrupts for one instruction. `rte` pops EXR word then the CCR+PC long. `trapa #n` uses vector 8+n and leaves the mask alone (from memory of the manual, unverified).
- Vector numbers match the standard H8S/2655 map: 28 ADI, 32 TGI0A (TPU0), 40 TGI1A, 44 TGI2A, 80/81/82/83 SCI0 ERI/RXI/TXI/TEI, 84 to 87 SCI1, 88 to 91 SCI2. So the firmware's live handlers are: 0xE0A16 (TPU0 compare A), 0xE0A72 (TPU1 compare A), 0xE0A44 (TPU2 compare A), SCI0 (80 to 82, MIDI), SCI1 (84 to 86: 0xE0ACC, 0xE0AA0, 0xE0AF8). The CPU stub at 0x104D4 handles all the unused vectors.
- Step 7 part 1 done. `onchip.go`: `AttachChip(cpu)` maps a device window 0xFFFE00 to 0xFFFFFF over the placeholder RAM; unmodelled registers read back what was written and are logged once per address and direction (`Chip.Unmodelled()`, printed by `emu.exe run`). A/D converter modelled: ADCSR 0xFFFF98 (ADF set at once on ADST, cleared only by a software write of 0, single or scan mode, ADI vector 28 if ADIE), results in ADDRA..D at 0xFFFF90 to 0xFFFF97 as 10 bit left justified; input values `Chip.AD[0..7]` default 0x3C0 (assumption). `TestBootPassesADWait` proves the boot gets past the poll at 0x105EBE.
- BIG FINDING: the CPU is an H8S/2600 core, not 2000. The kernel's context switch at 0x107AA to 0x107B0 uses `ldmac er0,mach` and `ldmac er0,macl` (opcodes 0x0320 and 0x0330). The decode table is now generated from MAME's h8s2600d.inc (made with `re/mame_h8/h8make.py h8.lst d s26 h8s2600d.inc`), adding clrmac, ldmac, stmac and mac. Implemented with a 42 bit accumulator `CPU.MAC` (mach = bits 32 to 41, sign extended on read). `mac @ern+,@erm+` is a plain signed 16 x 16 accumulate without saturation or the MAC flags (unverified, check if the firmware uses it: grep `mac ` in the listing). The Ghidra module probably lacks these four instructions too (it had 2 undecoded of 150,000 samples), worth adding to the sleigh spec later.
- Boot problem from the previous firing SOLVED, two causes, both CPU semantics:
  1. Interrupt control mode: the firmware runs in MODE 0 (SYSCR is never written, `INTM` = 0 at reset). The task switcher tests the config byte at 0x127F0 (bit 1 clear = no EXR in frames) and skips the EXR word with `adds.l #2,sp` before `rte`. My step 6 assumed mode 2, so `rte` popped a word too many. `CPU.IntMode` (0 or 2, set from SYSCR bits 5:4 in `onchip.go`) now selects: mode 0 = I bit masks interrupts, frame is CCR + 24 bit PC, accept sets I; mode 2 = EXR priority levels, EXR word in the frame. Test `TestMode0FrameAndMask`. The earlier note that the kernel stub at 0x104D4 proves mode 2 was wrong (it reads both layouts' bytes).
  2. PC bit 0 is always 0 in hardware. The kernel's service call stubs (e.g. 0x12588 to 0x125A6) push a return address with bit 0 SET (`bset #0,r1l`) as a marker and the final `rte` is expected to ignore it. `Step` now clears PC bit 0 before fetching. Test `TestPCBitZeroIgnored`.

- BUG FOUND AND FIXED (stm/ldm order): the boot burned hundreds of millions of instructions in a delay loop because a task switch corrupted er4..er6. The firmware's interrupt entry builds task frames by hand (pushes er4, er5, er6 in that order) and the switcher restores with `ldm.l @sp+,er4-er6`. So `stm.l` pushes the LOWEST register first (highest ends on top of the stack) and `ldm.l` pops the highest first. The old order was backwards; fixed in `step.go`, test updated. (This was the cause of the earlier 'er4 becomes 0x407EEE' symptom.)
